# Vercel + VM 기능별 분리 배포 계획 (초안)

**요청을 받고 바로 끝나는 기능은 Vercel**, **계속 실행돼야 하는 기능은 VM**에 둡니다.

## VM 구조

우리는 돈이 없으므로 학교 서버(VM)을 활용해 배포하겠습니다.

**특이 사항**

- 포트포워딩을 통해 내부 포트와 통신
- 자체 도메인 보유중
- 퍼블릭 접근 가능

## 분리 기준

기능의 주제(도메인)가 아니라 **실행 특성**으로 나눕니다.

| 특성                                                         | 배포 위치 |
| ------------------------------------------------------------ | --------- |
| 요청 → 응답으로 끝남, 상태 없음, 수 초 안에 끝남             | Vercel    |
| 연결을 유지해야 함 (WebSocket)                               | VM        |
| 정해진 시각에 실행돼야 함 (예약 작업)                        | VM        |
| 오래 걸리거나 재시도가 필요함 (AI, 외부 API 수집, 푸시 발송) | VM        |

## 기능별 배치

| 기능                                        | 위치   | 메모                            |
| ------------------------------------------- | ------ | ------------------------------- |
| 웹 화면 (Next.js)                           | Vercel | 현재 그대로                     |
| 로그인·세션·로그아웃 (웹, 앱 토큰 발급)     | Vercel | 현재 그대로                     |
| 커밋 기록, 수면·식사 기록 저장·조회         | Vercel |                                 |
| 걸음 수 동기화                              | Vercel | 짧고 덮어쓰기라 서버리스에 적합 |
| 스냅샷, 목표 가져오기, 친구, 경쟁 조회·순위 | Vercel | 순위는 조회 시 계산             |
| 채팅 기록 조회 (이전 메시지 페이지)         | Vercel |                                 |
| 상점, 칭호, 신고 접수, 관리자 화면          | Vercel |                                 |
| **채팅 실시간 송수신, 실시간 알림**         | VM     | Socket.IO 게이트웨이            |
| **급식 API 수집**                           | VM     | 예약 작업                       |
| **급식 사진 AI 판정**                       | VM     | 작업 큐 워커                    |
| **푸시 알림 발송 (APNs, FCM)**              | VM     | 작업 큐 워커, 실패 시 재시도    |

**원칙: 사용자의 핵심 동작(로그인, 기록 저장, 조회)은 모두 Vercel에 둡니다.**
VM이 멈춰도 기록은 계속 쌓이고, 실시간 채팅·AI 판정·예약 작업만 늦어집니다. 밀린 작업은 DB에 남아 있다가 VM이 돌아오면 이어서 처리됩니다.

## 전체 구조

```text
                         ┌──────────────── Vercel ────────────────┐
 웹 브라우저 ──HTTPS────▶│ web (Next.js)  /api/* rewrite ─▶ api    │
 네이티브 앱 ──HTTPS────▶│ api (NestJS, 서버리스)                  │
                         └───────┬───────────────────────┬────────┘
                                 │ pooled 연결            │ 작업 등록 (Job 테이블 INSERT)
                                 ▼                        │ 이벤트 등록 (Outbox INSERT + NOTIFY)
                         ┌─────────────── PostgreSQL (Neon) ──────┐
                         │ 유일한 데이터 저장소 = 두 쪽의 연결 지점 │
                         └───────▲───────────────────────▲────────┘
                                 │ direct 연결            │ LISTEN / 작업 가져가기
                         ┌───────┴──────────── VM ────────┴────────┐
 웹·앱 ──WSS (티켓)────▶│ realtime  (Socket.IO 게이트웨이)        │
                         │ worker    (작업 큐: AI 판정, 푸시 발송)  │
                         │ scheduler (급식 수집, 일일 판정, 마감)   │
                         │ (+ 급식 사진 저장소)                     │
                         └─────────────────────────────────────────┘
```

### Vercel과 VM은 서로 직접 호출하지 않습니다

**DB를 통해 데이터만 주고받습니다.**
서로 상호작용하지 않음

| 방향                        | 방식                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Vercel → VM (작업)          | API가 `Job` 행을 저장 → VM 워커가 가져가서 처리. 큐 라이브러리는 PostgreSQL 기반 **pg-boss** 사용 (Redis 불필요) |
| Vercel → VM (실시간 이벤트) | API가 `Outbox` 행 저장 + `NOTIFY` → VM이 `LISTEN`으로 받아 소켓으로 전달 (예: "OO님이 커밋!")                    |
| VM → 사용자                 | 처리 결과는 DB에 저장. 웹·앱은 Vercel API로 조회하거나 소켓 이벤트로 받음                                        |

- 이벤트를 놓쳐도 `Outbox`에 남아 있으므로, VM이 재시작하면 아직 처리하지 않은 행부터 다시 보냅니다.
- `LISTEN`은 Neon의 pooled 연결에서 동작하지 않으므로 VM은 **direct 연결**을 씁니다. VM은 상시 실행이라 연결 몇 개만 유지하면 됩니다.

## 실시간 연결 인증 — 티켓 방식

현재 세션 쿠키는 웹 도메인 전용(`__Host-`, host-only)이라 VM 도메인으로는 전송되지 않습니다. Vercel rewrite도 WebSocket 연결을 넘겨주지 못합니다. 쿠키 정책을 바꾸는 대신 **일회용 티켓**을 씁니다.

1. 웹이 `POST /api/realtime/ticket`을 호출합니다. 기존처럼 세션 쿠키와 CSRF로 인증합니다.
2. Vercel API가 30초짜리 일회용 티켓을 만들어 해시를 DB에 저장하고, 원문을 응답합니다.
3. 웹이 `wss://rt.<도메인>`에 티켓을 담아 연결합니다.
4. VM이 `Origin`을 확인하고, DB에서 티켓을 한 번만 소비한 뒤 사용자로 연결을 승인합니다.

네이티브 앱은 이미 Bearer access token을 갖고 있으므로 그 토큰으로 바로 연결합니다.

## 급식 사진 AI 판정 흐름

1. 앱이 Vercel API에 식사 기록을 만듭니다. `aiVerdict = PENDING` 상태가 되고, 사진 업로드용 일회용 티켓을 받습니다.
2. 앱이 VM의 업로드 엔드포인트로 사진을 보냅니다. 사진은 VM 디스크에 저장됩니다.
3. VM이 판정 작업을 큐에 넣고, 워커가 AI를 호출해 결과를 DB에 저장합니다.
4. 결과는 소켓 이벤트로 알리고, 앱은 Vercel API로 기록을 다시 조회합니다.

사진을 VM에 두면 워커가 바로 읽을 수 있어 단순합니다. 대신 VM 디스크 백업이 필수입니다. 외부 객체 저장소(Cloudflare R2 등)를 쓰면 두 쪽 모두 접근할 수 있지만 관리할 플랫폼이 하나 늘어납니다.

## 코드 구조 — 하나의 NestJS 코드, 진입점 두 개

서버를 두 개의 프로젝트로 나누지 않습니다. 도메인 로직, Prisma, 인증은 함께 쓰고 **진입점과 루트 모듈만 나눕니다.**

```text
apps/server/src/
├─ main.ts                # Vercel: ApiModule (HTTP 컨트롤러만)
├─ vm.ts                  # VM: VmModule (realtime + worker + scheduler 한 프로세스)
├─ api.module.ts          # 컨트롤러가 있는 모듈들
├─ vm.module.ts           # Gateway, 큐 워커, @nestjs/schedule 작업
├─ modules/               # auth, commits, steps, chat, quests ... (양쪽 공용 서비스)
├─ jobs/                  # 작업 이름·페이로드 타입 (양쪽이 같은 정의를 씀)
└─ realtime/              # 티켓 검증, Socket.IO 게이트웨이, Outbox 리스너
```

- VM에서는 우선 하나의 프로세스로 시작합니다. 부하가 생기면 같은 이미지를 역할별로 따로 띄울 수 있게, 진입점에서 역할을 환경변수로 고르게 해 둡니다.
- 예약 작업이 두 번 실행되지 않도록 VM은 **한 대, 한 프로세스**로 유지합니다. 여러 대로 늘릴 때는 pg-boss의 스케줄 기능처럼 DB 잠금을 쓰는 방식으로 바꿉니다.

## 도메인과 네트워크

- **자체 도메인이 필요합니다.** `commit-health.vercel.app`에는 VM용 하위 도메인을 붙일 수 없습니다.
  - 예: `app.<도메인>` (Vercel), `rt.<도메인>` (VM의 실시간 연결·사진 업로드)
- Google OAuth 리디렉션 URI와 서버의 `FRONTEND_URL`, `CORS_ORIGIN`, `GOOGLE_CALLBACK_URL`은 새 웹 도메인으로 바꿉니다.

## 환경변수

| 변수                                           | Vercel api          | VM  |
| ---------------------------------------------- | ------------------- | --- |
| `DATABASE_URL` (pooled)                        | O                   |     |
| `DATABASE_URL_UNPOOLED` (direct)               | 마이그레이션 작업만 | O   |
| `GOOGLE_*`, `FRONTEND_URL`, `COOKIE_SAME_SITE` | O                   |     |
| `CORS_ORIGIN` / 실시간 허용 Origin             | O                   | O   |
| AI API 키, APNs·FCM 키                         |                     | O   |
| 사진 저장 경로                                 |                     | O   |

AI·푸시 키를 VM에만 두면 Vercel 쪽 비밀값이 늘지 않습니다.

## 배포와 마이그레이션

- **Vercel**: 지금 방식 그대로 `main` 머지 시 자동 배포
- **VM**: CI가 서버 이미지를 빌드해 GHCR에 올리고, VM의 self-hosted runner가 `docker compose pull && up -d` 실행
- 작업 페이로드와 Outbox 이벤트에도 버전 필드를 두어, 이전 버전 워커가 새 형식을 받았을 때 건너뛰고 재시도할 수 있게 합니다.
- 마이그레이션 실행은 지금처럼 승인 후 수동으로 합니다.

## 장애 시 동작

| 상황        | 영향                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| VM 중단     | 로그인·기록·조회는 정상. 채팅은 폴링으로 전환, AI 판정·예약 작업은 대기 후 재개 |
| Vercel 장애 | 웹·앱 사용 불가. VM의 예약 작업은 계속 실행, 채팅 전송 비활성                                     |
| DB 장애     | 전체 중단. 두 쪽 모두 DB에 의존하므로 백업·복구 절차가 가장 중요                |

VM 중단 시 채팅이 폴링으로 돌아가게 하려면, 웹의 채팅 훅이 소켓 연결에 실패하면 폴링으로 내려가도록 만들어 둡니다.
